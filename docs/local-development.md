## Целевая конфигурация

Сервер читает локальный `.env` через собственную загрузку конфигурации или безопасную dotenv-библиотеку, а не исполняет его как shell script. Файл, БД, кэш и реальные артефакты исключаются из Git. `.env.example` должен содержать только имена и безопасные значения/пустые секреты.

| Переменная | Назначение / исходное значение |
| --- | --- |
| `HTTP_ADDR` | `127.0.0.1:8080` |
| `SQLITE_PATH` | `data/paper-scout.sqlite` |
| `CACHE_DIR` | `data/cache` |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` |
| `DEEPSEEK_MODEL` | Явно заданная доступная Chat Completions модель, проверяется preflight |
| `DEEPSEEK_API_KEY` | Секрет; только на сервере |
| `DEEPSEEK_THINKING` | `disabled` в начальном прототипе |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` |
| `EMBEDDING_MODEL` | `qwen3-embedding:0.6b` |
| `EMBEDDING_DIMENSIONS` | `1024` |
| `SEED_USER_1_LOGIN`, `SEED_USER_2_LOGIN` | Логины двух аккаунтов |
| `SEED_USER_1_PASSWORD`, `SEED_USER_2_PASSWORD` | Локальные пароли, не передаются аргументами командной строки |

Клиенту передаётся только адрес Go API; DeepSeek и Ollama не вызываются из Flutter напрямую. Bcrypt для паролей берётся из [golang.org/x/crypto/bcrypt](https://pkg.go.dev/golang.org/x/crypto/bcrypt); SQL driver — [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite). Эти библиотеки не предоставляют агентный runtime.

## Целевой порядок первого запуска

1. Подготовить `.env` и локальный каталог данных; секреты не вставлять в документацию и логи.
2. Выполнить `make doctor`: проверить SDK, `pdftotext`, FTS5, конфигурацию моделей и Ollama. Платный DeepSeek preflight запускается явно, а не скрыто при каждом health check.
3. Выполнить `make seed`: миграции и создание двух отсутствующих пользователей без сброса существующих.
4. Выполнить `make run`: Go API на loopback.
5. Запустить выбранный AVD, выполнить `adb reverse tcp:8080 tcp:8080` и передать Flutter адрес `http://127.0.0.1:8080`.
6. Из каталога `client/` выполнить `flutter run --dart-define=API_BASE_URL=http://127.0.0.1:8080`.

В debug Android разрешается локальный HTTP. Сервер остаётся на loopback и доступен приложению через adb reverse. Браузерный frontend, LAN-доступ и production TLS не требуются для этого прототипа.

## Целевые проверки

- `make check`: форматирование, Go build/vet, Flutter analyze и сборка debug APK.
- `make integration`: интеграционный набор с локальными fixtures и временной БД.
- `make integration-live`: явно включённый набор с реальными arXiv, DeepSeek и Ollama, ограниченным бюджетом и артефактами.

Unit/widget tests не генерировать и не писать. Из автоматически созданного Flutter skeleton не оставлять шаблонные unit/widget tests. Проверки документации и ацикличности DAG не являются тестами приложения.

## Управление устройством

Для управления Android-эмулятором и выполнения действий в интерфейсе Flutter используется `claude-in-mobile`. Это обязательный инструмент сквозной проверки и прохождения сценария демонстрации. Его подключение к выбранному эмулятору проверяется перед T13 и T16; наличие и работоспособность подключения на стадии документации ещё не проверены.

`adb` используется для технических операций: подключения локального API через reverse, установки сборки, захвата экрана и получения видеофайла. Действия пользователя в приложении выполняются через `claude-in-mobile`.

## Запись после готовности сценария

Целевой скрипт `scripts/record-demo.sh` должен запускать Android screen recording, сохранять MP4 с эмулятора через adb, проверять код завершения и файл. Во время записи сценарием приложения управляют через `claude-in-mobile`. После записи проверить воспроизведение, длительность и несколько кадров, затем пройти матрицу приёмки. Командная поддержка и ограничения `screenrecord` уточняются у выбранного запущенного AVD до записи; сценарий длиннее лимита утилиты разбивается на явно обозначенные части.

На этапе документации видео не записывается, эмулятор не запускается, ключи не запрашиваются и платные вызовы не выполняются.
