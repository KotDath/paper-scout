# Долговременная память исследователя: исследование подходов и рекомендация

Дата: 2026-10-18. Исследовательская основа выбранного дизайна; реализация ещё не выполнена.
Прочитаны README, черновик `docs/research-memory.md`, определения `Analysis`,
`Observations`, `Claim` в `internal/research/analysis_types.go`. Исходное исследование выполнено отдельным субагентом read-only; координатор сохраняет результат в docs.
Платные API, dotenv, библиотеки агентов/памяти не использовались.

## Рекомендация для Paper Scout

Нужна обязательная **фаза записи и консолидации исследовательской памяти**, а не
только поиск по Markdown старых отчётов. Минимальный вариант реализуется своим Go
кодом: неизменяемый исследовательский эпизод + производные типизированные карточки
методов/результатов/ограничений + версии пользовательских заметок и исправлений.
Recall автоматически срабатывает в новом диалоге; окончательное научное сравнение
проверяется по оригинальным passages. SQLite хранит данные и отношения, существующие
Qwen3/BM25/RRF их находят. Neo4j, отдельный агент или memory framework не нужны.

**Дополнительный LLM write-pass сейчас не нужен.** Анализатор уже возвращает
`Claim{Text,EvidenceIDs}`, `Observations{Methods,Results,Limitations}`, `Synthesis`,
источники и coverage. Мы уже заплатили за извлечение и синтез. Детерминированная
bounded проекция этих структур даст атомарные научные наблюдения с более ясным
происхождением, чем повторное сжатие всего отчёта ещё одной моделью. Это рекомендация
для имеющихся данных, а не утверждение, что извлечение без LLM вообще лучше.

Первые изменения к черновику: добавить write/consolidation lifecycle и typed cards;
не ограничиваться `report`/`note` chunks; сохранить публичную ссылку на эпизод/отчёт,
но передавать модели отдельный научный claim с facet, источником, evidence и статусом.

## Что показывают пять подходов

Таблица — пересказ первичных источников. Оценка применимости/сложности — наше
инженерное суждение для Paper Scout, а не опубликованный benchmark.

| Подход | Запись и устройство памяти | Обновление/конфликт/забывание | Чтение, происхождение и применимость |
|---|---|---|---|
| [MemGPT, §2](https://arxiv.org/html/2310.08560v2#S2) | Иерархия: ограниченный working context, история сообщений в recall storage, долговременный архив. Модель вызывает функции чтения/записи и управляет переносом контекста. | Eviction сообщений из prompt не удаляет архив; сводка сохраняет контекст. Рабочие заметки редактируются моделью. Фактологические ревизии не являются основным предметом этой архитектуры. | Полезны ограниченный контекст, отдельный архив и адресуемая история. Полностью отдавать модели решение «вспомнить ли что-то» рискованно для нашего обязательного A→B сценария; нужен автоматический recall. Несколько tool/LLM шагов увеличивают стоимость. |
| [Mem0, §2](https://arxiv.org/html/2504.19413v1#S2) | Из нового обмена и контекста LLM извлекает краткие сведения; похожие записи подаются LLM для консолидации. Вариант Mem0g хранит сущности и отношения. | Операции ADD/UPDATE/DELETE/NOOP; graph-вариант может признавать отношения недействительными, сохраняя историю. | Берём lifecycle и дедупликацию. Для научного помощника LLM-решение DELETE недостаточно обосновано: новая формулировка может относиться к другому эксперименту. Извлечение и update требуют дополнительных вызовов. |
| [A-MEM, §3](https://arxiv.org/html/2502.12110v1#S3) | Атомарная заметка включает исходное взаимодействие, дату, сгенерированные keywords/tags/context, embedding и связи. Из ближайших соседей LLM строит связи. | Новая заметка может вызвать evolution контекста/keywords/tags старых. Статья описывает замену предыдущей производной заметки. | Полезны атомарность и связи между эпизодами. Не берём автономную перезапись научного содержания: ошибка в одном эпизоде может изменить интерпретацию старых. Соседние LLM-обновления добавляют стоимость на запись. |
| [Zep/Graphiti, §§2–3](https://arxiv.org/html/2501.13956v1#S2) | Отдельны исходные episodes, производные semantic entities/facts и community summaries. Производные факты связаны с источниками. | Bi-temporal данные разделяют время события и время появления/инвалидации в системе; конфликт может ограничить интервал старого факта без потери эпизода. | Полезнее всего provenance и ревизии. Гибридные кандидаты, обход связей, reranking дают несколько путей retrieval. Полная graph extraction/resolution/community система избыточна для локального прототипа; простые SQL relations достаточны. |
| [Reflexion, §§2,5](https://arxiv.org/html/2303.11366v4) | После результата/обратной связи агент формирует текстовый урок и использует его в следующих попытках. Это память о способе действия, а не только о содержании документа. | Ограниченный буфер рефлексий; качество зависит от feedback/evaluator. Возможны локальные неоптимальные стратегии. | Для нас полезен принцип «исправление пользователя меняет следующий подход». Саморефлексия без проверяемого feedback не доказывает корректность урока. Отдельный автоматический рефлектор пока не нужен. |

В современном [Letta API](https://docs.letta.com/v1-sdk/concepts/stateful-agents)
stateful agent объединяет system prompt, memory blocks, сообщения и tools; важные
blocks находятся в контексте, старые сообщения сохраняются после eviction. Это
подтверждает полезное разделение постоянной пользовательской настройки, архива и
текущего контекста, но не требует использовать Letta как зависимость.

В [официальном Graphiti edge_operations.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/utils/maintenance/edge_operations.py)
видны episode attribution, временные поля и инвалидация ранее известных отношений.
Мы переносим идею отслеживаемой ревизии, а не этот код или инфраструктуру.

## Что считать памятью в нашем продукте

Это разделение — предлагаемый контракт Paper Scout; перечисленные работы не
используют единую обязательную классификацию episodic/semantic/procedural.

| Вид | Конкретные данные | Что означает достоверность |
|---|---|---|
| Эпизодическая | Исследование: вопрос, report/run/conversation IDs, время, выбранные статьи, coverage, итог и ошибки | Доказательство того, что было сделано и сказано, а не того, что вывод истинен |
| Семантическая исследовательская | Атомарные методы, результаты, ограничения из сохранённого анализа; paper/version/document, evidence IDs | Вывод модели с проверяемым первоисточником; существование evidence ID не гарантирует entailment |
| Пользовательская | Явная заметка, критерий выбора, исправление, предпочтение; автор, scope, версия | Достоверно, что это сказал пользователь. Его научное утверждение всё ещё требует сверки с источником |
| Процедурная | Явное указание «в следующих исследованиях сравнивай длительность диалогов» или проверенный урок после feedback | Меняет способ работы в соответствующем scope; не превращается в универсальный системный prompt |

Не надо объявлять всякий note предпочтением: «авторы не проверили X» — научная
оценка/гипотеза, а «для меня важно X» — критерий пользователя. Без нового извлечения
все свободные заметки безопасно сохранять как `user_annotation`; явные профильные
поля остаются typed preferences. Если первый релиз не классифицирует заметки,
он должен передавать их точный текст с автором, не выдумывать им семантический тип.

## Минимальный write/update/read lifecycle

### 1. Запись после эпизода

После атомарной публикации отчёта создаётся durable pending-задание на projection
либо память пишется в той же короткой транзакции. Упавший index worker не должен
терять факт завершения эпизода; startup подбирает pending. Embeddings всегда вне
SQL-транзакции; неопубликованная или отменённая работа не становится успешным опытом.

Проекция берёт `Analysis.Synthesis` — ограниченный набор `Methods/Results/Limitations`.
Если synthesis нет, допускаются только успешные observations с `partial` и точным
coverage. Нельзя использовать успешный prefix без предупреждения о неполноте.
Выбор одного уровня исключает дублирование одинаковых claims из каждой части и
итогового synthesis. Существующий analysis остаётся источником правды; карточки
полностью восстанавливаемы из него.

Каждая карточка содержит: owner, immutable ID/revision, kind/facet, claim text,
origin analysis/report/run, paper/version/document, evidence IDs, coverage/status,
created_at, hash и origin revision. Метаданные embedding включают model/digest,
dimension и формат ввода. Научные citations проверяются по существующим ownership
и passage contracts; отслеживаются не только текстовые `ev_...` в Markdown.

Ограничить число/суммарный текст карточек на эпизод и размер батча. Непоместившиеся
карточки не выбрасывать молча: source analysis доступен по ссылке, projection
получает явный статус, оставшийся bounded backlog можно обработать позднее.

### 2. Консолидация и ревизии

- `ADD`: новая карточка со своим origin/evidence.
- `NOOP`: тот же origin revision либо точный нормализованный claim+facet+paper version
  уже проецирован. Повторный запуск не создаёт копии.
- Сходный claim из другого исследования **не NOOP автоматически**: сохранить
  дополнительное происхождение и новую наблюдаемую evidence связь. Embedding
  similarity даёт кандидатов, но не доказывает эквивалентность.
- `REVISION`: пользователь отредактировал note/profile — новая версия, прежняя
  недействительна для текущего recall. Исторический run snapshot неизменен.
- `RELATED`: совпадает paper/version или подтверждена явная ссылка между эпизодами.
  Иные похожие записи достаточно находить retrieval; не строить LLM-граф заранее.
- `DISPUTED`/`CORRECTION`: явная правка пользователя связывается с конкретной
  карточкой/утверждением, если target известен. Научный claim помечается спорным,
  а исходный анализ не переписывается. Новый ответ должен проверить оригинал.
  Новая подтверждённая трактовка может `supersede` старую derived-карточку, сохраняя
  обе ревизии и evidence. Несогласие двух разных статей — не автоматическое
  опровержение и не last-write-wins.

Для минимального UI существующая заметка к статье может выступать paper-scoped
feedback: при recall связанных claims приложить её целиком. Система должна
понимать, что note изменился, но не обязана угадывать, какую фразу старого отчёта
он формально опровергает. Точную машинную retraction стоит разрешать только при
явном target/операции, а не после эвристического поиска слова «не».

Первый релиз не нуждается в выдуманном автоматическом forgetting score: source
episodes сохраняются, текущий recall исключает superseded/retracted/deleted
user annotations. Временная нерелевантность понижает выдачу, не удаляет научный
материал. Очистка note удаляет его текст из будущей выдачи и embeddings, а не
воскрешает старую версию при rebuild. Исторический snapshot отражает прошлый
доступ и не должен использоваться как текущая заметка.

### 3. Recall в новом диалоге

До первого DeepSeek вызова автоматически искать по текущему вопросу среди текущих
semantic cards и episodic passages. Owner фильтруется **до** каждого top-k.
Использовать существующие Qwen3, BM25 и RRF; общий RRF не должен позволять длинному
отчёту занять все места. Группировать по paper/origin, брать разные facets.

Затем детерминированно расширить найденные origins актуальными notes/corrections
по тем же papers/targets. Нельзя заставлять заметку конкурировать за единственный
top-k со всеми chunks: исправление может не содержать терминов нового вопроса,
но менять смысл найденного claim. Ограниченный профиль/явные глобальные критерии
передаются отдельно. Не нужна полная история всех диалогов в prompt.

Есть два уровня recall: перед первым вызовом — вопрос; после выбора статьи B или
получения её analysis — один bounded дополнительный recall по methods/limitations
и метаданным B. Название B может ничего не говорить о релевантном A. Этот второй
проход использует уже полученные данные, не требует ещё одного извлекающего LLM.

Снимок выдачи фиксирует ids/revisions/text/hash/provenance/mode/reasons и кандидаты,
фактически попавшие в prompt. Число found/recalled отдельно от referenced/used:
инъекция в контекст не доказывает, что память повлияла на решение. В final output
нужно различать пользовательский критерий, прошлый вывод и новый научный факт.

### 4. Научное сравнение и накопление

Научное утверждение A/B подтверждается оригинальными passages обеих работ через
существующий `read_passages`. Старый generated report/card — навигатор и память
об исследовании. Он не становится новым первичным evidence. Связь сравнения
сохраняется вместе с новым эпизодом как проверяемый результат, а не переписывает A.

Пример желательного поведения: «Раньше мы изучили A; вы попросили отдельно оценивать
длительные диалоги. В B другой механизм; по этим passages эксперимент не позволяет
сделать тот же вывод, что A». Текст и отличия выбираются по реальным источникам,
а не зашиваются в prompt. Не требуется генерировать сравнение, если связь слабая.

Всё передаётся как помеченные данные, не новые system instructions. Источники,
прошлые ответы и notes не могут снять ограничения безопасности/ownership/tool
budgets. Любая дополнительная модельная операция — через единственный gateway,
с общим token/request budget и durable accounting.

## Чем это функционально отличается от «индексируем Markdown»

1. После каждого исследования есть явная write/consolidation операция, её состояние
   проверяемо; хранится не только набор разрезанных строк отчёта.
2. Methods/results/limitations доступны отдельно, с paper version и прямыми evidence
   связями; можно сопоставить одну и ту же грань разных работ.
3. Правка пользователя меняет текущую память, не теряется среди похожих chunks и
   не стирает историю. Ошибочный вывод может быть явно помечен спорным.
4. Retrieval автоматически предшествует новому исследованию и повторяется bounded
   после появления содержания B. Пользователь не обязан назвать A.
5. Научные факты, прежние выводы и предпочтения не смешиваются в один «профиль».
   Именно это защищает от закрепления hallucination через повторное пересказывание.

Это не обучение весов и не обещание автономного «самосовершенствования». Это
проверяемое изменение доступного знания и способа анализа между отдельными сессиями.

## Ограничения доказательств в статьях

- MemGPT проверял чат и задачи retrieval/document QA; успешное вспоминание факта
  не доказывает корректное сравнение научных методов или обработку исправлений.
  [Первичный текст](https://arxiv.org/html/2310.08560v2#S3).
- Mem0 оценивался на LoCoMo и исключил adversarial/unanswerable категорию; baseline
  RAG ограничен выбранными chunk/k настройками, а оценки частично LLM-as-a-judge.
  Его относительные проценты и экономию нельзя переносить на DeepSeek/наши статьи.
  [Методика](https://arxiv.org/html/2504.19413v1#S3).
- A-MEM использует conversational QA; сама статья признаёт зависимость организации
  памяти от LLM. Грамотно расположенные embeddings не доказывают истинность связей.
  [Ограничения](https://arxiv.org/html/2502.12110v1#S6).
- Zep прямо отмечает малый DMR: 60 сообщений и простое извлечение. В статье
  provenance-переходы к episodes не являлись отдельным предметом экспериментов.
  [Оценка](https://arxiv.org/html/2501.13956v1#S4).
- Reflexion оценивает улучшение последующих попыток с feedback, а не надёжность
  произвольного долговременного научного знания. Нужен наблюдаемый сигнал качества.
  [Ограничения](https://arxiv.org/html/2303.11366v4#S5).

Не строить сводный рейтинг этих процентов: модели, датасеты, judges, контексты и
операционные затраты несопоставимы. [LongMemEval](https://arxiv.org/abs/2410.10813)
отдельно проверяет extraction, multi-session reasoning, temporal reasoning,
knowledge updates и abstention; эти оси полезнее для нашей приёмки, чем один QA score.
Однако ни один из перечисленных результатов не заменяет нашей проверки научных
цитат, UI, владельцев и сохранения после рестарта.

## Проверяемые критерии для реализации

1. **Обязательная запись:** исследование A порождает durable episode и typed
   method/result/limitation cards с валидными origins/evidence. После rebuild
   те же источники доступны без оплаченного повторного анализа.
2. **Идемпотентность:** повтор projection A — NOOP; новый эпизод с тем же выводом
   не теряет новое происхождение и не раздувает recall дубликатами.
3. **Новый диалог:** A → содержательная note → restart Go/Flutter → B без A в
   вопросе. До первого запроса модели видны automatic recall и точный snapshot.
4. **Межстатейная связь:** после получения B при необходимости работает один
   bounded content-based recall. Содержательная связь с A появляется самостоятельно.
5. **Смысловое влияние:** новый ответ указывает прежний отчёт, реально применяет
   пользовательский критерий и сравнивает соответствующие facets A/B. Три
   утверждения сверяются вручную по passages обеих работ.
6. **Corrections:** note edit/clear обновляет будущий recall после restart/rebuild;
   старый текст не всплывает через episodic snapshots. Явное оспаривание конкретного
   claim помечает его и заставляет проверить первоисточник; не происходит silent
   удаления scientific facts.
7. **Противоречия:** две статьи с разными результатами сохраняются вместе с
   условиями эксперимента. Система не выбирает «правду» только по recency.
8. **Ошибка агента:** намеренно неверный старый вывод с существующим evidence ID
   не считается доказанным; новая проверка выявляет несоответствие и сохраняет
   исправление/ограничение. Нельзя тестировать только синтаксис citation.
9. **Негативный recall:** несвязанный вопрос не приводит к выдуманному сравнению;
   отсутствие evidence приводит к оговорке/abstention, не к «вспомненному факту».
10. **Изоляция:** второй аккаунт не получает ни cards, ни notes, ни episode metadata,
    ни прямые memory links; обе ветки фильтруют owner до кандидатов.
11. **Гонки/сбои:** edit во время embedding не публикует старую ready revision;
    backlog/restart/cancel/outage дают явные статусы и сохраняют original report.
12. **Бюджет:** верхняя граница карточек, batching, recall char/token cap, <=2
    автоматических точек recall в run; no unbounded rebuild, без hidden LLM retries.
    Логи раздельно считают memory write/read, embedding и DeepSeek usage.
13. **Контроль пользы:** тот же запрос B при отключённой memory не знает личный
    критерий и прошлый эпизод A; при включённой — корректно использует их. Не
    сравнивать стилевую красоту ответов вместо проверяемого факта использования.
14. **Основной продукт:** live-проход через `cmd/paper-scout`, Flutter и
    claude-in-mobile, реальные источники/DeepSeek/Ollama; новый отдельный видеоролик.
    Fixtures допустимы для race/отказов; unit/widget tests запрещены.

Координатор выбрал описанный минимальный механизм. Точные схемы и границы первого релиза: [research-memory.md](research-memory.md), DAG T19–T22. Сравнительная записка не является заявлением о готовности реализации.
