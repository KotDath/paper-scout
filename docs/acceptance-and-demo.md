## Интеграционные проверки

Тесты проверяют работающие HTTP-маршруты вместе с БД и настоящими внутренними модулями. Допустим подменный HTTP endpoint внешней системы для воспроизводимого сбоя, но не изолированный unit test функции с моками всех соседей.

1. **Авторизация и ownership:** два аккаунта; чужие conversation/run/report/evidence недоступны; logout отзывает токен.
2. **Run и история:** HTTP-создание, повтор `client_request_id`, tool-enabled обмен через внешний HTTP fixture, сохранение сообщений и итогового отчёта.
3. **Тексты:** HTML и текстовый PDF с несколькими страницами проходят весь ingestion; повреждённый/пустой текст даёт честную причину. Для fixtures использовать собственные или разрешённые к хранению тексты.
4. **Полное покрытие:** анализ нескольких последовательных частей; пропущенная/ошибочная часть не позволяет выставить `complete`.
5. **Гибридный retrieval:** обе ветки проходят через индекс и EmbeddingClient; fusion с известными ранжированиями проверяется через HTTP endpoint на небольшом корпусе. В live-режиме используются реальные embeddings.
6. **Изоляция retrieval:** чужие chunks не участвуют в кандидатах ни BM25, ни dense; общий публичный кэш не даёт доступа к чужим заметкам.
7. **Недоступные зависимости:** ошибки DeepSeek/arXiv/Ollama сохраняются с причиной, retries ограничены; lexical fallback не называется hybrid.
8. **Отмена и рестарт:** остановка длинного run; после перезапуска он `interrupted`, готовые данные сохранены; автоматический платный replay отсутствует.

Не создавать unit tests для RRF, JSON helper, chunk splitter или отдельных методов только ради покрытия. Проверять нужное поведение через интеграционный путь. Отдельный live-набор запускается явно и с ограниченным расходом.

## Реальная проверка перед записью

- Зафиксировать commit, версии окружения, DeepSeek model, embedding model/digest и время запуска.
- Пройти новый вопрос через Flutter с реальными arXiv, DeepSeek и Ollama. Cache hits допускаются, но отмечаются; для доказательства сетевого получения хотя бы одного источника нужен новый fetch, а не только ранее сохранённый ответ.
- Получить хотя бы одну работу с полностью разобранным извлечённым текстом. Открыть её методику или ограничения, проверить фрагмент и ссылку на оригинал.
- Задать уточняющий вопрос. Убедиться, что обе ветки retrieval выполнены и найденный evidence использован в ответе.
- Для небольшого размеченного набора вопросов проверить точный термин, перефразировку и русский вопрос по английскому тексту. Сохранить ожидаемые evidence IDs и фактический top-8.
- Перезапустить сервер/приложение, открыть сохранённый результат, затем войти вторым аккаунтом и проверить отдельную историю.

Проверка осмысленности ответа включает минимум три содержательных утверждения: источник существует, фрагмент действительно поддерживает утверждение, статус полного/частичного чтения соответствует trace. Существование URL само по себе недостаточно.

## Сценарий видео

Все действия в интерфейсе эмулятора выполняются через `claude-in-mobile`. Захват видео и перенос MP4 выполняются средствами записи, описанными в runbook.

Ориентир — 4–7 минут, если реальный поиск и анализ укладываются; длительность уточняется после прогона. Запись показывает реальные действия. Если приходится сокращать ожидание монтажом, это явно обозначается; готовый ответ не изображается новым live-run.

1. Кратко назвать задачу: «Я отслеживаю исследования о долговременной памяти AI-агентов; сервис помогает находить и разбирать работы».
2. Войти первым аккаунтом, показать интересы и ввести конкретный вопрос.
3. Запустить исследование; показать этапы поиска, получения полного текста и анализа. Прогресс основан на событиях сервера.
4. Открыть отчёт, выбранную статью, отметку покрытия и подтверждающий фрагмент со страницей/разделом. Проверить один содержательный вывод по источнику.
5. Задать follow-up о методике/ограничении. Открыть доказательные фрагменты и детали гибридного retrieval.
6. Сохранить статью и заметку, перезапустить приложение, открыть результат из истории.
7. Сменить аккаунт и показать отдельную историю. Полную HTTP-проверку изоляции приложить в артефакт приёмки.
8. Завершить кратким результатом автоматизации; добавить сведения о Go, Flutter и собственном harness.

Основное видео пишется с Android-эмулятора. Перезапуск Go и технические проверки можно подтвердить отдельным журналом; нельзя заявлять, что они видны на видео, если кадры их не содержат. Если требуются пояснения голосом, звук записывается отдельно: Android `screenrecord` сам по себе не является записью микрофона.
