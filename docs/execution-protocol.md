# Протокол выполнения DAG

Пользователь разрешил запуск реализации с отдельным Git worktree и веткой для каждой ноды, двумя циклами ревью и последующим упрощением в третьем потоке. Оркестрация разработки через BB не является агентной библиотекой продукта.

## Исполнители ноды

Для каждой ноды создаются три постоянных BB-потока в её worktree:

1. **Исполнитель** реализует задачу, проверяет её, фиксирует коммит. В этот же поток возвращаются оба набора замечаний.
2. **Ревьюер** читает diff от зафиксированного base SHA, задачу, план, архитектуру и состояние графа. Не меняет код. Два раза выдаёт конкретные замечания; после каждого ревью исполнитель исправляет код и повторяет относящиеся к нему проверки.
3. **Упрощатель** после обоих циклов читает весь diff и удаляет ненужные дублирования/сущности с сохранением поведения. Проверяет изменения и фиксирует отдельный коммит. Если упрощать нечего, подтверждает это с основанием.

После упрощения ревьюер проверяет закрытие замечаний и отсутствие регрессий от упрощения. Это итоговый контроль, а не замена двух полных циклов. Неразрешённая существенная проблема останавливает слияние ноды.

Технический workflow-worker координирует эти потоки и сохраняет результаты, сам не реализует продукт. Роли наследуют используемые в исходном потоке provider/model/reasoning; при запуске сверены Codex, `gpt-6.1-sol`, `high`.

## Ветки и исходные данные

Ветка ноды — `dag/tNN`; worktree находится в соседнем каталоге `paper-scout-worktrees/TNN`. Base SHA фиксируется при запуске ноды после слияния всех её зависимостей. Независимые ноды получают собственные worktrees и не изменяют файлы друг друга.

Каждой роли передаются задача, критерий выхода, актуальный на момент старта снимок графа, точный base SHA и пути к документации в её worktree. Ревью и упрощение дополнительно получают актуальный diff и результаты предыдущего этапа.

Одновременно выполняются до трёх независимых нод. Это начальное ограничение оркестрации для предотвращения перегрузки; остальные готовые ноды ставятся в очередь. Нода проходит свои этапы сразу, независимо от стадии других веток. Глобального барьера «все реализовали, затем все ревьюят» нет.

## Слияние

Слияния выполняются последовательно в исходной `main`. Интегратор проверяет base, ревью, чистоту worktree и diff, сливает ветку, разрешает обычные конфликты с сохранением обоих изменений и запускает подходящие интеграционные/сборочные проверки. Конфликт поведения, который нельзя разрешить уверенно, не маскируется успешным merge.

Нода получает `done` только после успешного слияния и проверки. Только после этого разрешается запуск зависимых нод. Статус и merge SHA записываются в `docs/execution-state.json`, а итоговый статус задачи — в `docs/implementation-tasks.json`.

## Состояние и восстановление

Workflow сохраняет историю вызовов BB. Дополнительно `.bb/runtime/nodes/TNN/ledger.json` содержит worktree, ветку, идентификаторы трёх потоков, этапы и проверки. Файлы сообщений, diff и ответы ролей лежат рядом и исключены из Git. Повтор координатора использует ledger и не создаёт заново уже завершённые этапы.

Каждый этап заканчивается структурированным результатом с уникальным именем этапа. Неудача провайдера или отсутствие ключа фиксируются как blocker, а не как успешная проверка. Независимые доступные ветки продолжают работу; потомки заблокированной ноды не запускаются. Корневой поток получает сообщение о blocker для устранения.

Ключ DeepSeek передаётся только через защищённый ввод BB в корневой `.env`. Модель не читает и не пересказывает его значение. Доступность ключа не разрешает неограниченный расход: реальные проверки выполняются с малыми бюджетами из проекта.

Сохранённый workflow — `.bb/workflows/implement-dag.js`; helper управления тремя потоками — `.bb/workflows/execute-node.py`. Перед запуском проверяется точный исходник workflow и корректность Python-синтаксиса. Эти проверки не являются юнит-тестами приложения.
