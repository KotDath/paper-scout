# T02 — Аккаунты и ownership

Дата: 2026-10-18. Ветка `dag/t02`.
Base: `01131aba83491b196e75ace742625a2fad0c1d57`.

Реализованы `T02_accounts.sql` (`users`, `auth_sessions`, `profiles`), явный
`-seed`, bcrypt-пароли, случайные bearer-сессии со сроком 24 часа и отзывом,
auth middleware, `/api/v1/auth/login`, `/api/v1/auth/logout`, `/api/v1/me`,
GET/PUT `/api/v1/profile`. Владелец берётся только из проверенной сессии;
SQL профиля ограничен `user_id`. Инструкция и интерфейс для следующих нод —
[accounts.md](../accounts.md).

Проверено на `go1.26.2-X:nodwarf5 linux/amd64`, SQLite через
`modernc.org/sqlite v1.60.1`, `golang.org/x/crypto v0.58.0`:

- `go mod tidy`: успешно. Из-за задержки proxy использованы копии уже
  закэшированных публичных зависимостей T01 в runtime T02, затем tidy завершён
  с `GOPROXY=off`. Исходный кэш не изменялся; модульные версии закреплены.
- `go build -mod=readonly -o .bb/runtime/t02/auth-check ./cmd/paper-scout`:
  успешно; интеграционные сценарии также самостоятельно собирают бинарник.
- `go vet ./...`: успешно.
- `python3 integration/accounts.py`: успешно. Реальные Go-процессы, HTTP и
  SQLite, генерируемые временные учётные данные, loopback-порт `0`, временная
  БД и все build caches внутри этого worktree. Моков нет.
- Seed: два аккаунта и профиля; bcrypt DefaultCost 10; повтор сохраняет ID,
  password hashes, timestamps, профили и сессии. Пустые/короткие/длинные пароли,
  совпавшие и неверные логины отклоняются без частичного создания аккаунтов.
- HTTP: вход обоих аккаунтов, `/me`, собственный профиль, независимое обновление
  интересов и 16 параллельных чтений. Неверные/отсутствующие credentials дают
  401 с одинаковым публичным сообщением. Избыточные поля владельца и query
  `user_id` дают 400; заголовок `X-User-ID` не меняет владельца.
- Профиль адресуется только `/profile` текущего пользователя. Запросы
  `/profile/{чужой_id}` и `/profile/{отсутствующий_id}` дают одинаковый 404,
  поскольку маршрута адресации профиля по ID нет. Дополнительно при удалённом
  собственном профиле GET/PUT возвращают 404 и не читают/не меняют существующий
  профиль другого аккаунта. Это проверка изоляции профилей, не доказательство
  ownership ещё не реализованных report/evidence.
- Logout даёт 204, последующие запросы с тем же токеном — 401; другие сессии
  того же и второго аккаунта остаются действующими. После рестарта профили и
  активная сессия доступны, отозванные токены по-прежнему отвергаются.
- Истечение проверено изменением `expires_at` временной SQLite-сессии на прошлую
  дату: запрос немедленно даёт 401, сессия второго аккаунта продолжает работать.
- Проверены SQL foreign keys, SQLite integrity, SHA-256 токена вместо plaintext,
  отсутствие паролей и исходных bearer-строк в файлах БД, лимит JSON 64 KiB,
  неверный JSON/тип тела, ограничения профиля, JSON-формат ошибок и `no-store`.
- `python3 integration/foundation.py`: успешно — health/readiness, FTS5/BM25,
  concurrent checks, WAL, права БД, dotenv precedence, graceful restart,
  сохранение ledger и строки, отказ на checksum drift, неверном HTTP_ADDR и
  обезличенная ошибка dotenv. Проверка количества миграций обновлена для
  нескольких task migrations вместо фиксированной единственной T01.

- `go mod verify`: `all modules verified`.
- `gofmt -l cmd internal`, `git diff --check`: успешно, вывода нет.
- Проверка tracked/unignored файлов: unit/widget tests отсутствуют и не
  создавались.
